# Фильтры статусов и безопасная загрузка WAV

Дата: 2026-07-23
Статус: согласовано к реализации

## Цели

- дать оператору быстрый доступ ко всем ошибкам, очереди и текущей обработке;
- сохранить поиск и пагинацию списка записей;
- восстановить и исправить загрузку WAV через веб;
- не предоставлять веб-контейнеру право записи в архив `/media/audio`;
- вынести путь загружаемых файлов в `.env`;
- сохранить пользовательское изменение заголовка страницы на `MFC Voice`.

## Фильтрация списка

Над списком размещается группа одиночных фильтров:

- `Все`;
- `Ошибки`;
- `В очереди`;
- `В работе`;
- `Готово`;
- `Без запуска`.

Каждый фильтр показывает глобальное количество записей соответствующего статуса. Счётчики не зависят от поисковой строки, чтобы всегда отражать полное состояние пайплайна.

Фильтр и поиск применяются совместно по правилу AND. При изменении фильтра или поисковой строки пагинация возвращается на первую страницу. Если выбранная запись не входит в отфильтрованный набор, выбирается первая видимая запись; при пустом результате панель деталей возвращается в состояние без выбора.

Фильтры реализуются кнопками с `aria-pressed`, доступны с клавиатуры и переносятся на мобильной ширине без нового breakpoint.

## Состояния

Отображение строится по `recording.job.status`:

| Фильтр | Значение |
|---|---|
| Ошибки | `failed` |
| В очереди | `pending` |
| В работе | `running` |
| Готово | `done` |
| Без запуска | запись без `job` |

Фильтр `Все` не ограничивает набор.

## Загрузка WAV

Архив записей остаётся смонтированным read-only:

```text
/media/audio -> /data/recordings:ro
```

Для файлов, загруженных через веб, используется отдельный host-каталог:

```text
VOICE_UPLOADS_HOST_DIR=./.uploads
```

В контейнерах он монтируется дочерним каталогом:

```text
${VOICE_UPLOADS_HOST_DIR:-./.uploads} -> /data/recordings/uploads
```

Права:

- `web`: read-write;
- `worker`: read-only;
- model API: доступ к исходному upload-каталогу не требуется, поскольку модели получают WAV через `/data/staging`.

Внутренний путь inbox задаётся отдельно:

```text
VOICE_UPLOADS_DIR=/data/recordings/uploads
```

Для локального запуска без Docker значение по умолчанию — `.recordings/uploads`.

`LocalDirectoryRecordingInbox` сохраняет WAV в uploads-каталог, но формирует идентификатор относительно общего recordings-root. Поэтому загруженная запись получает тот же безопасный `rel-<hex>` формат, что и прочие вложенные записи, и затем корректно находится `LocalDirectoryRecordingSource`.

Имя файла продолжает очищаться до basename. Запись остаётся атомарной: временный файл проверяется как WAV и переименовывается только после успешной валидации.

## Конфигурация Compose

Базовый и prod Compose используют одинаковые имена переменных:

- `VOICE_RECORDINGS_DIR` — внутренний корень источника записей;
- `VOICE_UPLOADS_DIR` — внутренний каталог web inbox;
- `VOICE_UPLOADS_HOST_DIR` — host-путь отдельного writable-каталога.

Prod override не делает `/media/audio` writable. Дочерний mount uploads добавляется только в `web` и `worker` с разными правами.

Также исправляется опечатка `redordings` в незакоммиченном prod-состоянии базового Compose.

## Ошибки API

Ожидаемые ошибки загрузки остаются клиентскими:

- не-WAV имя или содержимое — HTTP 400;
- отсутствие настроенного inbox — HTTP 501.

Ошибки файловой системы не маскируются как успешная загрузка. В рамках этой задачи не вводится новый формат API-ошибок; корректный writable mount устраняет текущий HTTP 500 на штатной загрузке.

## Тестирование

До реализации добавляются падающие тесты:

- HTML содержит загрузку, поиск, pagination, live-индикатор и статусные фильтры;
- JavaScript хранит активный статус, объединяет статус с поиском, сбрасывает страницу и синхронизирует выбор;
- все шесть фильтров имеют ожидаемые значения и счётчики;
- inbox в дочернем uploads-каталоге возвращает идентификатор, который source может прочитать из общего корня;
- настройки читают `VOICE_UPLOADS_DIR`;
- Compose монтирует uploads read-write в `web`, read-only в `worker` и сохраняет `/media/audio` read-only;
- существующие тесты загрузки, поиска и пагинации продолжают проходить.

После реализации выполняются:

```bash
pytest -q
ruff check .
ruff format --check .
```

На prod проверяются:

- `/health`;
- количество записей и распределение статусов;
- успешный `POST /api/recordings` с тестовым WAV;
- появление загруженной записи в списке;
- переход задания из `pending` в `running` и далее в терминальное состояние.

Тестовый WAV после проверки не удаляется автоматически, поскольку удаление исходной записи не предусмотрено API.

## Не входит в задачу

- массовый retry старых Qwen-ошибок;
- изменение формата отчёта;
- серверная пагинация или серверная фильтрация;
- изменение модели RabbitMQ;
- предоставление `web` права записи в `/media/audio`.
